Malgary VPN Architecture

Where each part fits in the pilot (cell c01, DigitalOcean New York), and how it grows to 100,000 users without a redesign. Constitution v2.0.0, plan for feature 001.

How a connection works

  1. 1The user clicks Connect in the NetBird app. The browser opens the Malgary sign-in page, which hands off to the customer's Google or Microsoft login, or uses email, password and MFA.
  2. 2The app fetches its configuration, keys and policies from that customer's own NetBird stack at onedge.vpn.<domain>.
  3. 3The app opens a WireGuard tunnel to the customer's routing peer on the active gateway.
  4. 4Traffic leaves the gateway from the reserved IP. Client systems allowlist this one address.
  5. 5Customer admins use the portal. You use the CLI now and the back-office later. Both go through the same backend API.
  6. 6The backend creates organizations and users in Zitadel, deploys each customer's NetBird stack, and sets their users, groups, routes and posture rules through the NetBird API.
  7. 7If gw-a fails, keepalived on gw-b asks the DigitalOcean API to move the reserved IP. Users reconnect within 60 seconds and the IP stays the same.

How each part grows

WhenWhat you add
New customerOne more NetBird stack on a control host, and one routing peer per gateway. Around 50 small customers fit on one host.
10 → 50 usersNothing new. Change sizes in configuration.
Busy gatewayResize the pair, then add a second pair with its own reserved IP.
New regionA gateway pair in that region (San Francisco, Atlanta, Kansas City).
Bigger platformPortal, backend and Zitadel move off the control host to their own servers. PostgreSQL moves to a dedicated or managed server.
Host or cell fullAdd a control host, or open cell c02. About 20 cells reach 100,000 users.
Dedicated IP add-onA gateway pair used by one customer only.
